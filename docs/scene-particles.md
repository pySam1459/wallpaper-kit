# Scene particles

`ImagePlayback::open_scene_images` prepares a bounded 2D particle profile alongside visible images, preserving authored object order. Explicit image selection with `open` and static snapshots remain image-only. Prepare assets off the UI thread, sample at the library clock time, then submit the returned composition through `Renderer::render_images`.

Supported components include box/sphere emitters, continuous and instantaneous births, random lifetime/size/color/alpha/velocity, gravity with nonnegative drag, alpha fades, size changes and alpha oscillation. Sprite quads, velocity-stretched sprite trails and bounded rope strips use static TEX textures with bilinear sampling, tint and additive or translucent blending. Death children spawn at the parent's final position; follow children attach to its current position. Layer transforms and count/rate/size/speed/alpha/color overrides apply. Start time prewarms a system, following the [official system description](https://docs.wallpaperengine.io/en/scene/particles/component/general.html).

[Particle profile compatibility](particle-profiles.md) adds box direction scaling,
sphere sign constraints, clockwise vector rotation in radians and nullable
particle defaults. It records the controlled engine geometry checks and the
nine newly prepared objects across five local wallpapers. Nonzero X/Y rotations
and other unsupported components remain explicitly reported.

`REFRACT=1` translucent particle materials prepare texture slot 1 as a normal map and validate `ui_editor_properties_refract_amount` in 0..=1. At each refractive quad, the GPU snapshots the prior composition, rotates the normal's XY displacement with the quad, samples the clamped background and blends using albedo alpha and particle opacity. Normal maps share existing source limits and stay resident across empty particle intervals. The independent displacement model is verified through generated GPU pixels; its exact engine scaling and blending still require a stable reference capture.

Scene discovery applies authored `hdr=true` when visual effects are enabled. The library accumulates code values in RGBA16F before resolving back to the existing RGBA8 output. Authored `bloom=false` disables the glow and its pyramid while retaining float accumulation and refraction. Scenes without a `bloom` field retain the existing default of applying the configured HDR bloom strength. A bounded independent bloom pyramid applies HDR threshold, feather, strength, scatter and 1..=16 integral iterations. The filter is an approximation, not verified Wallpaper Engine bloom fidelity. `ImagePlaybackReport::hdr_bloom` records HDR pipeline activation, including zero-strength or disabled bloom. Explicit image selection and static snapshots remain SDR. Selected precise/cloud effects still reject HDR, and HDR image-brightness overrides are not implemented. See the [official HDR bloom description](https://docs.wallpaperengine.io/en/scene/effects/bloom.html) for the intended scene behavior.

HDR uses one output-sized float target; refraction adds one reusable background snapshot. Bloom levels halve each dimension until the requested count or 1 x 1. At the public output size limit, these targets consume at most about 299 MiB, excluding the existing blur scratch, source textures, output pool, consumer textures and driver memory. `OutputStats::effect_texture_bytes` reports admitted float-target bytes. Allocation and readback stay on the renderer worker. A full-target GPU copy per refractive quad can be expensive; these limits do not establish a frame-time budget.

Sampling derives births from time and fixed library seeds. Seeking backward needs no history replay. The same time and assets reproduce the same descriptors and GPU output. This approximates engine behavior; it does not reproduce the engine's random sequence or integration scheme. At saturation, the oldest living births in the bounded window are drawn; engine admission history is not reproduced. Count overrides bound simultaneous/instantaneous particles; the authored rate override controls continuous emission.

Opening admits at most 32 particle objects, 32 definitions per object and four nested definitions along a child path. Cycles fail with context. Sampling shares a scene-wide budget of 32,768 birth evaluations and 4,096 particle quads; excess work/draws is dropped in authored order. Images retain their 32-layer limit. Static decoding and unique composition pages retain the 256 MiB bound. Prepared particle sources remain resident across empty intervals to avoid repeated uploads. These bounds do not establish total process memory or frame time.

Unsupported components/materials are named in playback omissions. Malformed supported numbers or missing assets fail with context. Scripts and live property updates are not evaluated. Boolean user-property bindings use their stored `value` default, so Gojo's stars/fireworks are visible and its clock remains hidden. Scene versions 1 and 5 are accepted, with a restricted `genericimage2` version-2 translucent image profile for version 1. Package signatures `PKGV0016`, `PKGV0018`, `PKGV0022` and `PKGV0024` use the checked index layout. Older `TEXB0003` PNG storage may use its checked unpadded content rectangle within the reserved header extent.

## Verify Gojo

The local [Gojo Satoru scene](https://steamcommunity.com/sharedfiles/filedetails/?id=2778759553) contains images `18,14`, stars `83`, shooting star `88`, and fireworks `1633`. Rocket death events create a refractive ring, flare and spark trails. Image pulse/water/shake effects, parallax and general camera/color settings remain omitted. Original assets remain read-only and outside source commits.

Build the examples and run from the repository root:

```powershell
cargo build --locked --examples
pwsh -File scripts/verify-gojo-particles.ps1 -ScenePath 'C:/Program Files (x86)/Steam/steamapps/workshop/content/431960/2778759553/scene.pkg' -EngineAssets 'C:/Program Files (x86)/Steam/steamapps/common/wallpaper_engine/assets'
```

Add `-Width 3840 -Height 2160` to verify the same scene at 4K. The controller checks the actual completed-frame dimensions before capturing.

The controller checks pinned package identity, image/particle discovery, HDR activation, ring admission, native captures at eight times, exact rewind, paused idle, eight retained source uploads, an eight-second live interval and owned-process exit. Generated public WARP contracts independently check additive pixels, rocket movement/death endpoints, trails/follow attachment, prewarming, ordering, texture retention, malformed counts and cycles. Additional contracts check normal direction, alpha, rotation, resize, overbright accumulation before resolve, bloom threshold/strength and invalid HDR settings. The disabled-bloom regression checks that no halo or bloom-pyramid allocations remain, while overbright accumulation is preserved. `scripts/verify.ps1` remains the required gate; its target-specific seven-image assertions use the original Yuta package.

The [HDR/refraction native receipt](../artifacts/gojo-hdr-refraction/report.json) records RTX 5080 hardware, 960 x 540 output, eight retained texture uploads, 9,677,576 effect bytes, exact rewind, paused idle and owned-process exit. It observed 237 live presentation calls during eight seconds with a maximum observed call gap of 44.66 ms. This establishes native rendering and resource reuse, not display cadence, GPU duration or host responsiveness.

Gojo authors `hdr=true` and `bloom=false`. The disabled-bloom correction is verified by the [before](../artifacts/gojo-fireworks-before-4k/report.json) and [after](../artifacts/gojo-fireworks-after-4k/report.json) RTX 5080 native runs at 3840 x 2160. At the same 4.75-second seek, the [prior white disk](../artifacts/gojo-fireworks-before-4k/time-04750.png) becomes an [authored flare with visible sparks](../artifacts/gojo-fireworks-after-4k/time-04750.png). Effect targets fall from 154,829,160 to 132,710,400 bytes, removing 22,118,760 bytes of bloom levels. Both runs record 238 live presentation calls in eight seconds, with maximum observed gaps of 34.64 and 34.78 ms respectively. These measurements establish the halo correction and removed allocations; they do not demonstrate a native cadence improvement. The [required gate](../artifacts/20261011-233510-3a0742cd/manifest.json) passed after the correction.
